### <strong>#원격 브랜치 정보 가져오기</strong>

지금까지 git pull 명령은 원격 저장소의 최신 커밋을 지역 저장소에 합쳐 준다는 것을 알아보았다. 하지만 원격 저장소의 최신 커밋을 무조건 합치지 않고 원격 브랜치에서 어떤 변화가 있었는지 그 정보만 가져온 후 필요한 커밋만 합칠 수도 있다. 이제부터 이 방법에 대해 공부해 보자.

#### <strong>커밋과 브랜치 이해하기</strong>

지역 저장소의 main 브랜치처럼 원격 저장소를 만들 때도 main 브랜치가 기본으로 만들어진다. 앞에서 git\_home 저장소와 git\_laptop 저장소로 원격 저장소를 복제한 상태로 실습해 보겠다.

> git log
{: data-ke-style="style3"}

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="630" data-origin-height="109"><span data-url="/assets/images/posts/af425af66afc9e9d53bf04ea4321c3899516ecdf.png" data-phocus="/assets/images/posts/af425af66afc9e9d53bf04ea4321c3899516ecdf.png"><img src="/assets/images/posts/af425af66afc9e9d53bf04ea4321c3899516ecdf.png" loading="lazy" width="630" height="109" data-origin-width="630" data-origin-height="109"></span></figure>

git\_home 디렉터리가 열려 있는 상태에서 git log 명령으로 커밋 상태를 확인해 보자.  최종 커밋인 'add day' 앞에 (HEAD -&gt; main, origin/main, origin/HEAD)라고 표시되어 있다. 여기에서 (HEAD -&gt; main)은 이 커밋이 지역 저장소의 최종 커밋이라는 뜻이고, (origin/main)은 원격 저장소의 최종 커밋이라는 뜻이다. 아직 git\_home 디렉터리가 원격 저장소를 복제한 상태 그대로이므로 지역  저장소와 원격 저장소의 최종 커밋이 같다.

> git add f3.txt  
> git commit -m "create f3.txt"
{: data-ke-style="style3"}

git\_home 디렉터리에 새로운 커밋을 만들어보겠다. f3.txt 파일을 만든 후 간단히 'a'라고 입력해 주었다. f3.txt를 스테이지에 올린 후 커밋을 만들어주는데, 커밋 메시지는 'create f3.txt'라고 하겠다.

> git log --oneline
{: data-ke-style="style3"}

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="378" data-origin-height="137"><span data-url="/assets/images/posts/2f5de3744d26147e72cf2d4d1ade718b10fbcffc.png" data-phocus="/assets/images/posts/2f5de3744d26147e72cf2d4d1ade718b10fbcffc.png"><img src="/assets/images/posts/2f5de3744d26147e72cf2d4d1ade718b10fbcffc.png" loading="lazy" width="378" height="137" data-origin-width="378" data-origin-height="137"></span></figure>

git log --oneline 명령을 사용해 커밋 로그를 한눈에 확인해 보았다. (HEAD -&gt; main)는 방금 커밋한 create f3.txt를 가리키고 있다. 지역 저장소의 최종 커밋이 create f3.txt 커밋이라는 뜻이다. 하지만 (origin/main, origin/HEAD)는 아직 add 9 커밋을 가리키고 있다.

> git status
{: data-ke-style="style3"}

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="469" data-origin-height="80"><span data-url="/assets/images/posts/3060c1fa95d733618a9c66f6bc124531d5f8b19e.png" data-phocus="/assets/images/posts/3060c1fa95d733618a9c66f6bc124531d5f8b19e.png"><img src="/assets/images/posts/3060c1fa95d733618a9c66f6bc124531d5f8b19e.png" loading="lazy" width="469" height="80" data-origin-width="469" data-origin-height="80"></span></figure>

이 상태에서 git status 명령을 입력해 주었다, 현재 지역 저장소의 main 브랜치가 원격 main 브랜치의 버전보다 하나 앞서 있다. 그리고 git push 명령으로 지역 저장소의 커밋을 원격 저장소로 올리라고 알려주고 있다.

> git push  
> git log --oneline
{: data-ke-style="style3"}

<figure class="imagegridblock"><div class="image-container"><span data-url="/assets/images/posts/5607e3865223fa07bdb1881597bdc457c80b65d2.png" data-phocus="/assets/images/posts/5607e3865223fa07bdb1881597bdc457c80b65d2.png" data-origin-width="487" data-origin-height="158" data-is-animation="false" style="width: 45.5898%; margin-right: 10px;" data-widthpercent="46.13"><img src="/assets/images/posts/5607e3865223fa07bdb1881597bdc457c80b65d2.png" loading="lazy" width="487" height="158"></span><span data-url="/assets/images/posts/659bff88f4df5881cb3ed310b8e7d9ca4190f1e6.png" data-phocus="/assets/images/posts/659bff88f4df5881cb3ed310b8e7d9ca4190f1e6.png" data-origin-width="450" data-origin-height="125" data-is-animation="false" style="width: 53.2474%;" data-widthpercent="53.87"><img src="/assets/images/posts/659bff88f4df5881cb3ed310b8e7d9ca4190f1e6.png" loading="lazy" width="450" height="125"></span></div></figure>

지역 저장소의 커밋을 원격 저장소로 올리기 위해 이제 git push 명령을 사용하겠다. 그 후에 커밋 로그를 확인해 보았다. 푸시하기 전까지는 main 브랜치와 origin/main 브랜치가 가리키는 커밋이 달랐지만, 푸시한 후에는 main 브랜치와 origin/main 브랜치가 같은 커밋을 가리킨다.

#### <strong>원격 브랜치 정보 가져오기 - git fetch</strong>

페치(fetch)는 '불러오다, 가져오다'라는 뜻이다. 그래서 git fetch 명령은 원격 저장소의 정보를 가져온다. 예를 한번 들어보자. 깃허브로 팀 작업을 할 때 다른 사람이 원격 저장소에서 수정한 내용을 가져와서 훑어본 후에 필요할 때만 지역 저장소에 합치는 상황을 생각해 보자. 이럴 경우 fetch 명령을 사용하면 변경된 내용을 가져오기만 할 수 있다.

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="503" data-origin-height="149"><span data-url="/assets/images/posts/aaade85f304a43396f7f5cdf28cb334abeae187d.png" data-phocus="/assets/images/posts/aaade85f304a43396f7f5cdf28cb334abeae187d.png"><img src="/assets/images/posts/aaade85f304a43396f7f5cdf28cb334abeae187d.png" loading="lazy" width="503" height="149" data-origin-width="503" data-origin-height="149"></span></figure>

현재 깃허브 저장소에는 creat f3.txt 커밋까지 올라간 상태이다. 이번에는 노트북 저장소로 이동해서 진행해 보겠다. git\_laptop 디렉터리가 열려 있는 VS Code로 이동한다. 원격 저장소의 변경 내용을 가져오기 위해 git pull 명령을 사용해야겠지만 여기에서는 git fetch 명령을 입력해 주겠다.

> ls -al
{: data-ke-style="style3"}

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="404" data-origin-height="128"><span data-url="/assets/images/posts/67eb5422c274fcc460530ed409d6afb6d038f35f.png" data-phocus="/assets/images/posts/67eb5422c274fcc460530ed409d6afb6d038f35f.png"><img src="/assets/images/posts/67eb5422c274fcc460530ed409d6afb6d038f35f.png" loading="lazy" width="404" height="128" data-origin-width="404" data-origin-height="128"></span></figure>

ls -al 명령을 사용해서 어떤 파일이 있는지 살펴보았다. 분명히 원격 저장소에 있던 커밋을 가져왔는데 git\_home에서 원격 저장소로 푸시했던 f3.txt 파일이 보이지 않는다. 한번 git log 명령을 사용해 커밋 로그를 살펴보자.

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="369" data-origin-height="107"><span data-url="/assets/images/posts/9e271ad53478474c1bc88611a9558aa58fa9f798.png" data-phocus="/assets/images/posts/9e271ad53478474c1bc88611a9558aa58fa9f798.png"><img src="/assets/images/posts/9e271ad53478474c1bc88611a9558aa58fa9f798.png" loading="lazy" width="369" height="107" data-origin-width="369" data-origin-height="107"></span></figure>

커밋 해시 오른쪽에는 (HEAD -&gt; main)만 보이고 원격 저장소의 origin/main은 보이지 않는다. 원격 저장소의 최신 커밋 정보를 가져왔지만 아직 지역 저장소에 합치지 않아 git\_office에 잇던 최신 커밋 (HEAD -&gt; main)만 나타나기 때문이다.

> git status
{: data-ke-style="style3"}

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="547" data-origin-height="82"><span data-url="/assets/images/posts/dc97c580c160846056133863c70b91f273a3b5ad.png" data-phocus="/assets/images/posts/dc97c580c160846056133863c70b91f273a3b5ad.png"><img src="/assets/images/posts/dc97c580c160846056133863c70b91f273a3b5ad.png" loading="lazy" width="547" height="82" data-origin-width="547" data-origin-height="82"></span></figure>

git status 명령으로 현재 깃의 상태를 확인해 보았다. 현재 브랜치가 origin/main에 비해 커밋 1개가 뒤처져 있다고 나온다. 즉, 원격 저장소의 최신 커밋 하나가 아직 지역 저장소에 반영되지 않았다는 뜻이다. git pull 명령을 사용하면 지역 저장소를 업데이트할 수 있다고 알려준다.

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="369" data-origin-height="161"><span data-url="/assets/images/posts/b238ec5e0db874ca3dd95f0427308c2464ddb5f2.png" data-phocus="/assets/images/posts/b238ec5e0db874ca3dd95f0427308c2464ddb5f2.png"><img src="/assets/images/posts/b238ec5e0db874ca3dd95f0427308c2464ddb5f2.png" loading="lazy" width="369" height="161" data-origin-width="369" data-origin-height="161"></span></figure>

그렇다면 페치로 가져온 커밋 정보는 어떻게 확인할 수 있을지 알아보자. git diff 명령을 사용해서 현재 최신 커밋과 원격 저장소에서 가져온 커밋의 차이를 살펴보면 된다. HEAD는 현재 최신 커밋을 나타내고, origin/main은 원격 저장소에서 가져온(페치) 커밋을 나타낸다.

> git merge origin/main
{: data-ke-style="style3"}

원격 저장소에서 가져온 커밋을 지역 저장소에 합치겠다고 결정했다면 merge 명령을 사용하면 된다.

<figure class="imageblock alignCenter" data-ke-mobilestyle="widthOrigin" data-origin-width="461" data-origin-height="121"><span data-url="/assets/images/posts/d9b180d075596fa97f857be5e5c41ead11141337.png" data-phocus="/assets/images/posts/d9b180d075596fa97f857be5e5c41ead11141337.png"><img src="/assets/images/posts/d9b180d075596fa97f857be5e5c41ead11141337.png" loading="lazy" width="461" height="121" data-origin-width="461" data-origin-height="121"></span></figure>

다시 깃 로그를 살펴보면 'create f3.txt'라는 최신 커밋이 지역 저장소에 반영된 것을 볼 수 있다.

### <strong>#협업의 기본 알아보기</strong>

깃허브 원격 저장소는 협업 도구로도 많이 사용한다. 깃허브에 프로젝트를 위한 저장소를 만들고 사용자별로 작업을 나누어 진행할 수 있다. 깃허브에서 어떻게 협업이 이루어지는지 기본 과정에 대해 알아보자.

#### <strong>협업과 브랜치</strong>

깃허브 원격 저장소를 활용하면 브랜치 기능을 통해 한 장소에서 여러 사람이 함께 작업할 수 있다. 여기서 브랜치란 main 브랜치와 구분 짓는 작업을 하기 위해 코드를 분리하는 것(분기)라고 공부하였다.

협업은 프로젝트를 여러 역할로 나누어 각 팀원들에게 할당하고 나중에 이것을 모두 모아서 하나로 완성하는 과정이다. 깃을 공부할 때 살펴봤던 브랜치의 동작 방법과 같아 보인다. 그래서 깃허브로 협업을 할 때 팀원들은 자신이 맡은 업무에 따라 서로 다른 브랜치를 만들어서 필요한 작업을 하고 나중에 병합해서 메인 프로젝트에 합친다.

그래서 깃허브에서 협업하려면 여러 가지 약속이 필요하다. 브랜치 이름을 어떻게 정할 것인지, 이슈 관리는 어떻게 할 것인지 등 처음부터 작업 규칙을 정해 놓고 시작해야 한다.

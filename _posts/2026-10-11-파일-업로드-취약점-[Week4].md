#### <strong># 파일 업로드 취약점</strong>

파일 업로드 기능은 웹 서비스에서 동영상, 이미지 등을 업로드하는 기능으로 이 기능 자체가 서비스의 주요 기능인 서비스도 다수 존재한다. 파일 업로드 취약점은 바로 이 파일 업로드 기능을 통해 악성 스크립트 파일인 <strong>웹셸</strong>이 업로드되는 취약점으로, 공격자는 악성 스크립트 파일을 통해 서버에 시스템 명령을 실행한다.정상적인 파일 업로드 과정의 경우 사용자는 업로드 폼으로 파일을 업로드하고, 이 파일을 전달받은 애플리케이션은 지정된 경로에 파일 업로드를 진행한다. 반면 공격자는 파일 업로드 시 악성 스크립트 파일인 웹셸을 업로드하는 것이다.

#### <strong>1. 공격 목표</strong>

파일 업로드 취약점은 웹셸을 통해 시스템 명령어를 실행할 수 있기 때문에 공격자는 서버와 데이터베이스 내 중요 정보 획득, 터널링을 통해 내부 침투 및 다른 서비스 접근, 내부망 악성 프로그램 유포 등이 가능하다.

> 일반적으로 데이터베이스 내 고객의 개인 정보 탈취가 목표이다. 이를 위해 파일 업로드 취약점으로 서버를 장악하고 데이터베이스에 접근하여 개인 정보를 탈취한다.  
>   
> 기업 내 기밀 정보 탈취가 목표라면 데이터베이스, 공유 폴더, FTP 서버 등에 접근하며 기밀 정보를 탈취한다.
{: data-ke-style="style3"}

> 파일 업로드 취약점의 공격 목표는 단순히 서버를 장악하는 것이 아닌, 해당 서버를 경유하여 내부 네트워크로 공격 범위를 넓혀 나가 돈이 되는 중요한 정보들을 취득하는 것이다.
{: data-ke-style="style3"}

#### <strong>2. 웹셸 동작 원리 이해</strong>

공격자는 웹 브라우저에서 웹셸에 접속한다. 그런 다음 입력 폼에서 시스템 명령어인 <strong>ipconfig</strong>를 입력하고 실행하면 서버 측 웹셸로 요청 메시지가 전송된다.

cmd 파라미터 값 ipconfig가 cmd 변수에 전달된다. 그리고 Runtime.getRuntime().exec (cmd) 코드를 통해 운영 체제로 ipconfig가 전달 및 실행되며, 그 결과를 다시 애플리케이션에서 받아온다.

결과를 받았지만 결과가 입력 스트림 형태이기 때문에 텍스트로 바로 출력할 수 없다. 입력 스 트림 형태를 텍스트로 변환하는 작업이 필요하므로 이에 대한 결과를 result 변수에 담는다. 그리고 모든 결과가 담긴 result 변수를 결과에 반환한다.

애플리케이션에서 응답 메시지를 반환하면 공격자 측에서 결과를 받아 웹 브라우저에 출력한다.

#### <strong># 공격 방법론</strong>

기본적으로 파일 업로드 취약점을 위해 공격 대상인 파일 업로드 기능이 필요하다. 따라서 기능을 찾는 것이 첫 번째 단계이다. 기능을 찾았다면 두 번째 단계로 업로드된 파일의 경로를 찾아야 한다. 경로를 알아야 접근을 할 수 있기 때문이다. 세 번째 단계로 업로드 기능에서 확장자 검증 로직이 존재하면 우회를 해야 한다. 악성 스크립트 파일인 웹셸을 업로드하기 위해서는 서버 측 확장자로 업로드되어야 하기 때문이다.

#### <strong>1. 기능 찾기</strong>

첫 번째 단계 <strong>기능 찾기</strong>는 파일 업로드 기능을 찾는 단계다. 예를 들어, 파일 다운로드 취약점은 파 일 다운로드 기능을 대상으로, SQL 인젝션은 사용자 입력값을 통해 SQL 구문을 완성한 후 DBMS에 질의하는 기능을 대상으로 취약점 분석을 진행해야 한다. 따라서 파일 업로드 취약 점 역시 파일 업로드 기능을 대상으로 분석을 진행해야 하므로 파일 업로드 기능을 가장 먼저 찾아야 한다.

가장 간단한 방법은 파일 업로드를 사용하는 기능들 위주로 살펴보는 것이다. 대표적으로 게시 판의 첨부 파일 업로드, 계정 설정 페이지의 프로필 사진 업로드, 채용 사이트의 포트폴리오 업 로드, 관리자 페이지의 업로드 등이 있다.

> 현재는 각 기업에서 보안 인식 제고 및 지속적인 취약점 진 단이 진행됨에 따라 인증되지 않은 사용자가 이용할 수 있는 기능은 매우 한정적이며, 권한에 따른 기능만 이용할 수 있다. 따라서 웹사이트 내 클릭을 통해 접근하는 일반적인 접근 방식은 파일 업로드 기능을 찾는 데 한계가 있다.
{: data-ke-style="style3"}

#### <strong>2. 업로드 경로 찾기</strong>

두 번째 단계는 업로드 후 파일의 경로를 찾는 <strong>업로드 경로 찾기</strong>다. 업로드된 웹셸에 접근을 해 야 공격이 가능하기 때문에, 만약 업로드 후 경로를 찾지 못하여 URL로 접근하지 못하면 공격에 실패한다.

> 이 단계는 공격의 성공 여부를 결정하기 때문에 매우 중요하다.
{: data-ke-style="style3"}

개발자에 따라 파일 업로드 기능의 구현 형태도 다양하지만, 목적과 보안에 따라 크게 2가지로 구분할 수 있다. 업로드 시 파일 <strong>URL을 반환하는 경우</strong>와 <strong>반환하지 않는 경우</strong>다.

> <strong><span style="color: #000000;">URL을 반환하는 경우</span></strong>
{: data-ke-style="style2"}

업로드된 파일에 사용자가 접근하거나 다른 사용자에게 공유, 접 근해야 하는 경우다. 

> <strong>URL을 반환하지 않는 경우</strong>
{: data-ke-style="style2"}

이미지와 달리 사용자의 직접 접근이 필요가 없는 경우, 또 는 보안을 고려하여 경로 노출을 방지하거나, 파일 접근을 제한하고 싶은 경우다.

사용자 접근이 필요한 이미지는 URL이 필요하지만, 보안을 위해 노출하고 싶지 않다면 이미지 뷰어를 사용한다. 대표적인 기능은 게시글 내 첨부 파일, 채팅 기능 내 파일 전송, 채용 페이지 내 첨부 파일, 문의 게시판 첨부 파일, 과제 제출 업로드 등이 있다.

#### <strong>3. 실제 파일명 찾기</strong>

업로드 경로를 찾았다면 서버에 업로드된 세 번째 단계는 실제 파일명 찾기다. 실제 파일명을 알아야 웹셸 URL을 정확하게 알 수 있고, 접근할 수 있다. 보통은 파일을 업로드하면 파일명 그대로 서버에 업로드된다고 알고 있지만, 대부분 서버 측에서 생성한 임의의 파일명으로 업로드된다. 파일 다운로드 시 웹 프록시 도구를 통해 전달되는 파라미터를 분석하면 실제 파일명을 쉽게 알아낼 수 있다.

예를 들어 사용자가 test.png라는 파일을 업로드하였다. 이 경우 파일 다운로드 시 요청되는 파일명 관련 파라미터가 하나고, 해당 파라미터의 값이 test.png라면 원본 파일명 그대로 서버 측에 업로드된 것이라고 추론할 수 있다.

> 서버 측에 업로드된 파일명이 다르기 때문에, 사용자들이 파일을 다운로드하면 업로드할 때의 원본 파일명으로 다운로드할 수 있도록 Content-Disposition 헤더의 filename 속성을 사용한다. 이를 통해 원본 파일명으로 파일을 다운로드받을 수 있다.
{: data-ke-style="style3"}

사용자 파일명을 한국어, 일본어, 중국어 같은 다국어 문자로 업로드하면 클라이언트와 서버 측 간의 문자 인코딩 불일치로 파일명이 깨져 그대로 업로드를 못하는 경우가 발생한다. 이런 경우 서버 측에서 파일명을 문자 깨짐 없이 생성 가능한 문자 세트로 생성한 후 업로드 하면 문제를 해결할 수 있다.

#### <strong>4. 파일 검증 우회</strong>

파일 검증의 종류에는 파일 확장자를 기반으로 검증하는 확장자 검증, Content-Type 헤더를 기반으로 검증하는 MIME 타입 검증, 파일 크기를 기반으로 검증하는 파일 사이즈 검증, 이미 지 유무를 검증하는 이미지 검증 등이 있다. 이 중 MIME 타입 검증, 파일 사이즈 검증, 이미지 검증은 단독으로 사용하면 보안 취약점을 완전히 방어하지 못한다.

#### <strong>MIME 타입 검증이 안전하지 않은 이유</strong>

MIMEMultipurpose Internet Mail Extensions는 파일의 형식과 내용을 정의하기 위한 표준으로, 파일 업 로드 시 파일 형식을 명확히 식별하기 위해 사용한다. 초기 웹에서는 파일 검증 방법 중 하나로 많이 사용되었지만 우회가 발생하기 때문에 이제는 단독으로 사용하지 않는다.

#### <strong>확장자 검증 우회</strong>

확장자 검증은 널리 사용하는 파일 검증 방법 중 하나로, 업로드되는 파일의 확장자를 확인하 여 파일의 업로드 여부를 결정하는 검증 방식이다. 공격자가 웹셸을 실행하려면 반드시 웹 애플 리케이션 서버에서 컴파일되는 서버 사이드 확장자를 사용해야 한다. 따라서 확장자 검증은 웹셸 실행을 막을 수 있는 핵심 방법이다. 그러나 안전하지 않은 방식으로 확장자 검증 로직을 구현하면 취약할 수 있다.

확장자 검증 방식에는 <strong>블랙리스트</strong> 방식과 <strong>화이트리스트</strong> 방식 2가지가 있다.

> <strong>블랙리스트</strong>
{: data-ke-style="style2"}

허용되지 않은 확장자만 차단하고 그 외는 허용하는 방식으로, 일반적으로 서버 사이드 확장자 인 php, jsp, asp, aspx 등이 블랙리스트에 포함된다.

> 정해져 있는 리스트만 허용하지 않으면 되기 때문에 개발자 입장에서는 간편하고, 사용자 입장에서는 다양한 확장자를 업로드할 수 있다는 장점이 있다. Ex) 자유 게시판, 자료실 등
{: data-ke-style="style3"}

> <strong>화이트리스트<br></strong>
{: data-ke-style="style2"}

특정 확장자만 업로드를 허용하고 그 외 확장자는 모두 차단하는 방식이 다. 업로드할 수 있는 확장자가 제한되어 사용자 입장에서는 불편할 수 있지만, 보안적으로는 화이트리스트 방식이 더 안전하다.

> Ex) 이미지 게시판, 문서 게시판, 포트폴리오 첨부, 상품 이미지 첨부 등
{: data-ke-style="style3"}

블랙리스트 방식은 허용되지 않는 확장자에 포함되지 않는 서버 사이드 확장자가 있을 경우 우회가 발생할 수 있고, 다양하게 우회될 수 있는 잠재적 가능 성이 있어 점차 블랙리스트 방식이 아닌 화이트리스트 방식을 많이 사용하고 있다.

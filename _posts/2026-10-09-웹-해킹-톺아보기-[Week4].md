#### <strong># 웹 해킹이란 무엇일까?</strong>

웹 해킹이란 웹 애플리케이션 해킹이라고 할 수 있다. 이제부터 웹 해킹이 무엇인지에 대해 하나씩 살펴보겠다.

웹 애플리케이션 해킹에 대해 알기 위해서는 웹 애플리케이션에 대해 알아야 한다.

> <strong><span style="color: #000000;">웹 애플리케이션이란?</span></strong>
{: data-ke-style="style2"}

애플리케이션은 우리가 자주 접하는 프로그램으로 계산기, 메모장, 구글 크롬과 같은 브라우저 등이 있으며 모바일 앱 또한 프로그램이다. 따라서 웹 애플리케이션은 웹에서 사용하는 프로그램이라고 할 수 있다.

이러한 프로그램들은 프로그래밍이라는 과정을 거쳐 개발하며 웹 애플리케이션을 작성하는 데 쓰는 대표적인 언어와 도구로는 JSP(자바), PHP, ASP, ASP.NET, 파이썬 등이 있다. 그리고 이런 웹 애플리케이션을 해킹하는 행위가 웹 애플리케이션 해킹, 즉 웹 해킹이다.

#### <strong># 웹 해킹은 왜 발생할까?</strong>

웹 해킹은 대부분 사용자 입력값에 대한 입력값 검증 미흡으로 발생한다. 다시 말해 사용자 입력값을 서버 측에서 받을 뒤 아무런 검증도 없이 사용한다는 것이다. 공격자는 공격 페이로드를 입력하여 기능에 따른 취약점을 발생시킬 수 있다.

> <strong>사용자 입력값은 꼭 받아야 할까?</strong>  
> 대부분의 웹 서비스는 사용자로부터 입력값을 받은 후에야 기능이 동작한다. 예를 들어 구글과 같은 검색 엔진 웹 서비스에서 검색어를 입력하고 요청을 해야만 검색 기능이 처리되고 원하는 결과가 웹 페이지에 출력되는데, 이때 검색어가 사용자 입력값이 된다. 회원 가입의 경우에도 아이디, 패스워드가 사용자 입력값이 된다. 만약 이런 정보들을 입력하지 못한다면 서비스를 이용할 수 없다.
{: data-ke-style="style3"}

#### <strong># 웹 해킹 공격 프로세스</strong>

웹 해킹 공격 프로세스는 아래와 같은 5단계를 거쳐 순서대로 진행한다.

> <strong><span style="color: #000000;">1단계 : 공격 대상 지정</span></strong>
{: data-ke-style="style2"}

<strong>공격 대상 지정</strong>은 웹 해킹 공격을 할 대상 사이트를 지정하는 것이다. 해커의 경우 돈이 될 법한 사이트를, 진단자라면 고객사에서 지정한 사이트일 것이다.

> <strong><span style="color: #000000;">2단계 : 정보 수집</span></strong>
{: data-ke-style="style2"}

<strong>정보 수집</strong>은 본격적인 공격을 수행함에 앞서 공격에 필요한 정보를 수집하는 단계이다. 도메인, 계정, 구글 해킹과 같은 검색 엔진을 이용하는 방법이 있다. 이를 <strong>공개 정보 수집(OSINT)</strong>라고 부른다.

\-&gt; 정보 수집은 취약점을 분석할 때도 하고, 공격을 할 때에도 한다.

> <strong><span style="color: #000000;">3단계 : 취약점 분석</span></strong>
{: data-ke-style="style2"}

<strong>취약점 분석</strong>은 각종 분석 기법을 통해 각 기능에 발생할 수 있는 취약점들을 판별하는 단계이다.

> <strong><span style="color: #000000;">4단계 : 공격</span></strong>
{: data-ke-style="style2"}

<strong>공격</strong>은 취약점 분석 단계에서 취약 기능이라 판단할 경우 공격을 진행하는 단계이다.

> <strong><span style="color: #000000;">5단계 : 결과 도출</span></strong>
{: data-ke-style="style2"}

<strong>결과 도출</strong>은 공격을 통해 얻은 정보들을 의미 잇는 결과물의 형태로 만드는 단계이다.

#### <strong># 웹의 탄생</strong>

> <strong><span style="color: #000000;">웹이란?</span></strong>
{: data-ke-style="style2"}

웹은 인터넷에 연결된 컴퓨터, 모바일을 비롯한 각종 디바이스로 정보를 공유할 수 있는 공간이다. 정확하게는 <strong>World Wide Web</strong>이라고 하며, 이를 줄여서 <strong>WWW, W3 WEB</strong>이라 부른다.

> <strong><span style="color: #000000;">웹 1.0</span></strong>
{: data-ke-style="style2"}

1994년부터 2004년까지 대부분의 웹사이트가 텍스트와 링크로 구성되었으며, 이때는 사용자가 글을 등록, 수정, 삭제 등 웹에 참여하는 행위는 할 수 없었고 일방적으로 운영자가 업로드한 정보를 제공만 받는 형태였다.

> <strong><span style="color: #000000;">웹 2.0</span></strong>
{: data-ke-style="style2"}

사용자의 참여와 공유가 가능했으며, 이때부터 본격적으로 사용자가 동영상, 이미지를 공유할 수 있게 되어 UCC, 커뮤티니가 생기는 등 사용자 간 교류가 발생하기 시작했다.

이후 웹 3.0, 시맨틱 웹, 웹 4.0, 유비쿼터스 웹가지 구분이 된다. 이는 웹 발전 흐름에 따라 시대별 특징을 설명하기 위해 개념적으로 구분한 것일 뿐 실 환경에서는 혼합되어 사용되기 때문에 사실상 구분 짓는 것은 의미가 없다.

#### <strong># 웹을 구성하는 3대 요소</strong>

> <strong><span style="color: #000000;">HTTP</span></strong>
{: data-ke-style="style2"}

웹 서버와 웹 클라이언트 간 통신을 할 수 있도록 지원하는 역할을 한다.

> <strong><span style="color: #000000;">URL</span></strong>
{: data-ke-style="style2"}

웹 클라이언트가 웹 서버로 자원을 요청할 수 있게 해 준다.

> <strong><span style="color: #000000;">HTML</span></strong>
{: data-ke-style="style2"}

웹 클라이언트가 웹 서버로 URL을 통해 자원을 요청한 후 HTML이 담긴 응답을 받으며, 웹 클라이언트 프로그램인 웹 브라우저가 이를 해석하여 구조화된 인터페이스를 출력해 사용자에게 보여준다.

#### <strong># URL 톺아보기</strong>

URL은 통합 자원 지시자로,  인터넷의 리소스를 가리키는 표준 명칭이며 서버의 자원을 요청할 때 사용된다. URL로 인터넷의 모든 리소스를 요청할 수 있다, 이때 HTTP뿐만 아니라 FTP, SMTP 관련된 자원 요청도 가능하다.

URL은 URI(Uniform Resource Identifier)라고도 불리는데, 이는 URL과 URN이 포함된 종합적인 개념이다. (URL은 URI의 한 부분이다.)

#### <strong>URL 문자열 구조</strong>

> http://www.test.co.kr/img/logo.png
{: data-ke-style="style3"}

> <strong><span style="color: #000000;">http</span></strong>
{: data-ke-style="style2"}

스키마 부분으로, 사용할 프로토콜이 명시되어 있다. 이 URL의 경우 'http' 프로토콜을 통해 자원을 요청한다는 것을 알 수 있다. 이 외에도 https, ftp, file 등이 있다. 알파벳으로 시작해야 하며 대소문자를 가리지 않고 프로토콜 뒤에 콜론(:)이 붙는다.

> <strong><span style="color: #000000;">www.test.co.kr</span></strong>
{: data-ke-style="style2"}

서버 주소인 호스트 부분은 자원을 가진 서버의 위치를 나타낸다. 웹 브라우저는 이 정보를 바탕으로 해당 서버의 IP 주소를 알아낸다. URL에서는 포트 번호를 명시할 수 있도록 스펙상 정해져 있지만, 일반적으로 많이 사용되는 HTTP는 80번 포트, HTTPS는 443번 포트를 기본으로 사용하기 때문에 따로 적지 않아도 된다.

> 즉, http://www.test.co.kr과 http://www.test.co.kr:80은 같은 의미이다.

#### <strong>#웹의 핵심 기술, HTTP</strong>

HTTP는 하이퍼텍스트 문서를 전송하기 위해 사용하는 프로토콜, 즉 통신 규약으로 웹의 핵심 기술이다. 여기서 하이퍼텍스트 문서는 HTML 파일을 뜻하고, 프로토콜은 컴퓨터 간 정보를 주고받을 때 통신 방법에 대한 규칙과 약속으로, 일종의 언어라고 볼 수 있다.

#### <strong>1. HTTP 버전</strong>

> <strong><span style="color: #000000;">HTTP/0.9</span></strong>
{: data-ke-style="style2"}

최초로 웹이 등장했을 때 HTTP는 오직 HTML을 받아오기 위해 만들어졌다. 따라서 버전 번호, 명세서도 없었으며 정식 사양이 아니었다. HTTP/0.9는 GET 메서드만 지원하며, 특별한 기능은 없다.

> <strong><span style="color: #000000;">HTTP/1.0</span></strong>
{: data-ke-style="style2"}

HTTP의 첫 정식 사양으로 RFC 1945(HTTP 프로토콜 동작 방식을 기술한 표준 문서)가 발행되었다. HTTP/1.0부터 POST, HEAD 메서드, 헤더를 지원하며, 요청의 결과를 알 수 있는 상태 코드가 추가되었다. 또한 HTML 파일 외 다른 파일도 전송이 가능하게 되었다. 하지만 각 요청마다 새로운 연결을 맺고, 끊고, 다시 새로운 연결을 맺는 비효율적인 비연결지향 방식으로, 성능이 떨어진다.

> <strong><span style="color: #000000;">HTTP/1.0+</span></strong>
{: data-ke-style="style2"}

HTTP/1.0+는 Keep-Alive 커넥션을 지원함으로써 HTTP/1.0의 비효율적인 방식이었던 여러 번 커넥션을 맺는 설계 문제를 해결했다.

> <strong>HTTP/1.1</strong>
{: data-ke-style="style2"}

HTTP/1.1부터 Keep-Alive는 명세에서 빠지고 기본으로 지속 연결이 활성화됐다. 모든 요청이 끝나면 Connection: close 헤더를 통해 연결 종료를 알린다. 또한 기존 GET, POST, HEAD 3가지뿐이었던 메서드가 OPTIONS, PUT, DELETE 등 다양하게 추가되었다.

> <strong><span style="color: #000000;">HTTP/2.0</span></strong>
{: data-ke-style="style2"}

하나의 웹 페이지를 보기 위해서 수십 개의 요청을 보내야 정상적으로 페이지를 볼 수 있는 등 여전히 문제였던 HTTP의 성능 문제 해결을 위해 등장한 버전이다. 멀티플렉싱 스트림, 헤더 압축, 서버 푸시 등 성능 향상에 초점을 둔 기능들이 추가됐다.

> <strong>비지속 연결</strong>
{: data-ke-style="style2"}

초기의 웹은 단순히 문서를 전달하는 방식이었으므로 지속 연결이 필요하지 않았다. 따라서 한 번의 요청과 응답 과정을 거치면 바로 연결을 끊어버렸다. 연결 과정에서는 3-Way HandShake 과정을 거쳐 연결한 후 실질적인 HTTP 통신인 요청과 응답을 받고 연결이 종료된다. 여기서 TCP를 구성하는 시간이 HTTP 통신하는 시간과 거의 비슷하다. 다만, 파일을 요청할 때마다 3-Way HandShake 후 요청 및 응답받고 연결을 종료를 반복하므로 굉장히 비효율적인 통신을 한다.

> <strong>지속 연결</strong>
{: data-ke-style="style2"}

헤더에 Connection: Keep-Alive가 명시되어 있으면 지속 연결을 사용한다는 것이다. HTTP/1.1부터는 Connection: Keep-Alive  헤더 필요 없이 기본으로 지속 연결을 한다. 지속 연결의 경우 단 한 번의 3-Way HandShake 과정으로 여러 번의 요청과 응답 과정을 거칠 수 있어 비지속 연결에 비해 시간이 확연히 단축된다는 것을 알 수 있다. 연결의 성능은 버전을 거듭할수록 향상된다.

#### <strong>3. 메시지</strong>

클라이언트의 웹 브라우저와 웹 서버는 통신을 할 때 서로 알아들을 수 있는 일정한 형식으로 대화를 한다. 일정한 형식이란 HTTP 메시지로, 웹 브라우저가 요청할 때 보내는 메시지를 <strong>요청 메시지</strong>라고 부르며, 웹 서버가 HTTP 요청 메시지를 받고 응답할 때 보내는 메시지를 <strong>응답 메시지</strong>라고 부른다.

메시지 구조는 크게 시작 줄, 메시지 헤더, 메시지 보디 이렇게 세 부분으로 이루어진다.

> <strong><span style="color: #000000;">시작줄</span></strong>
{: data-ke-style="style2"}

요청 메시지일 경우 무엇을 요청하고 어떻게 해야 될지, 응답 메시지일 경우 요청에 대한 결과가 어떻게 됐는지를 나타낸다.

> <strong><span style="color: #000000;">메시지 헤더</span></strong>
{: data-ke-style="style2"}

요청과 응답의 상세 속성 정보로, 이름과 값으로 구성되며 콜론(:)으로 구분한다. 또한 메시지 헤더가 끝나면 개행 문자가 들어간다.

> <strong><span style="color: #000000;">메시지 보디</span></strong>
{: data-ke-style="style2"}

요청 메시지일 경우 사용자 입력값이나 전송할 데이터를 실어 보내고, 응답 메시지일 경우 클라이언트가 요청한 자원에 대한 데이터를 실어서 보낸다. 시작 줄과 메시지 헤더와 달리 이진 데이터 혹은 텍스트 등 다양한 타입의 데이터가 올 수 있다. 메시지 보디는 메시지 성격에 따라 존재할 수도 있고 존재하지 않을 수도 있다. 각 줄 마지막에는 개행 문자(텍스트 한 줄이 끝났음을 표시하는 문자 또는 문자열)로 문자열을 끝낸다.

#### <strong>응답 메시지</strong>

응답 메시지는 상태 라인, 메시지 헤더, 메시지 보디로 구성된다.

> <strong><span style="color: #000000;">상태 라인</span></strong>
{: data-ke-style="style2"}

버전, 상태 코드, 응답 문구가 들어간다. 또한 사용하는 HTTP 버전과 요청에 대한 결과를 나타내는 상태 코드로, 세 자리의 숫자로 되어 있으며 응답 문구에는 결과에 대한 설명이 담겨 있고 모든 필드는 공백으로 구분된다.

> <strong><span style="color: #000000;">메시지 헤더</span></strong>
{: data-ke-style="style2"}

시작 줄 다음 줄에 표기되며, 헤더는 응답의 속성과 추가 정보를 나타낸다. 헤더에는 요청 헤더, 응답 헤더, 일반 헤더, 엔티티 헤더 4가지로 분류된다.

> <strong><span style="color: #000000;">메시지 보디</span></strong>
{: data-ke-style="style2"}

엔티티 보디가 들어가며, 메시지의 데이터가 들어가는 부분으로 데이터 수송을 목정으로 설계했다. 이를 통해 이미지, 동영상, HTML 등 여러 가지 데이터를 실을 수 있다. 엔티티 본문은 선택적으로 있을 수도 있고 없을 수도 있다.

#### <strong>4. 메서드</strong>

<strong>HTTP 메서드</strong>는 요청 메시지 시작 줄의 요청 라인 제일 첫 번째로 포함되며, 자원을 어떻게 처리해야 하는지 서버로 알려준다.

#### <strong>GET 메서드</strong>

<strong>GET 메서드</strong>는 가장 오래 그리고 가장 많이 사용되는 메서드로, 웹 서버로 자원을 요청한다. 먼저 웹 브라우저에서 임의의 사이트 접속 시 GET 메서드를 통해 요청 메시지를 만든다. GET 메서드를 통해 데이터를 전송할 수 있는데, 이때 요청 라인의 요청 URL에 예약 문자 ?, =, &amp;를 이용하여 데이터를 전송한다. GET 메서드로 데이터를 전송하면 클라이언트 측에서는 브라우저 기록에 남고, 서버 측에서는 액세스 로그에 기록이 남는다.

#### <strong>POST 메서드</strong>

<strong>POST 메서드</strong>는 엔티티 본문의 데이터를 전송하는 메서드로, 서버에 데이터를 입력하기 위해 설계되었다. 예를 들어 회원 정보, 게시글, 아이디/패스워드 입력 등이 있다. POST 메서드는 GET 메서드와 달리 데이터를 엔티티 본문에 싣는다.

따라서 GET 메서드와는 데이터 전송 방식과 용도가 다르다. GET 메서드는 자원을 얻기 위해 사용하고 POST 메서드는 데이터를 입력하기 위해 사용한다.

#### <strong>HEAD 메서드</strong>

<strong>HEAD 메서드</strong>는 GET 메서드와 기능은 동일하지만, HEAD 메서드는 서버에서 응답으로 상태 라인, 응답 헤더만 반환하고 엔티티 본문은 반환하지 않는다. 또한 요청 URL에 대한 유효성과 헤더를 조사하기 위해 사용한다.

#### <strong>OPTIONS 메서드</strong>

<strong>OPTIONS 메서드</strong>는 요청 URL에 대해 지원 혹은 허용되는 메서드를 알기 위해 사용한다. 요청 자원에 <strong>&#42;</strong> 문자를 사용하면 웹 서버가 지원하는 메서드를 물어볼 수 있다. 응답 메시지에 *Allow* 헤더가 포함되며, 해당 헤더 내 지원하거나 허용하는 메서드를 확인할 수 있다. 이때 특정 자원에 대한 지원 메서드를 확인할 경우 자원을 입력하면 된다.

#### <strong>PUT 메서드</strong>

<strong>PUT 메서드</strong>는 서버에 자원을 생성한다. 이때 사용하는 요청 URL은 자원이 생성될 경로며, 엔티티 본문은 자원에 대한 내용이 들어간다. 또한 공격자가 악의적인 파일을 업로드하는 웹셸(웹에서 사용하는 셸)과 같은 공격에 이용된다.

#### <strong>DELETE 메서드</strong>

<strong>DELETE 메서드</strong>는 자원 삭제를 요청하는 메서드다. 요청 URL의 자원 삭제 요청 등 PUT과 마찬가지로 보안상 문제가 있어 일반적인 웹은 DELETE 메서드를 허용하지 않는다.

#### <strong>5. 상태 코드</strong>

<strong>상태 코드</strong>는 HTTP 통신은 클라이언트가 요청할 경우 서버는 요청에 대한 상세 결과를 알려주는 것을 말한다. 상태 코드는 세 자리 숫자로 구성되어 있으며 뒤에 응답 문구가 붙는다. 응답 문구는 상태 코드에 대한 설명이다.

#### <strong>상태 코드의 분류</strong>

상태 코드는 100번대부터 500번대까지 크게 5가지 분류가 있다. 100번대는 정보 상태 코드, 200번대는 성공 상태 코드, 300번대는 리다이렉션 상태 코드, 400번대는 클라이언트 에러 상태 코드, 500번대는 서버 에러 상태 코드로 분류된다.

<strong>●&nbsp;200&nbsp;OK:</strong> 클라이언트 요청이 정상적으로 처리되었음을 나타내며, 엔티티 본문은 요청에 대한 리소스를 포  
함한다. 단, 요청된 메서드에 따라 다를 수 있다. 예를 들어 GET 메서드는 요청에 대한 자원을 엔티티 본문에   
실어 보내지만, HEAD 메서드는 엔티티 본문 없이 응답 헤더만 세팅되어 전송된다.  
<strong>●&nbsp;301&nbsp;Moved&nbsp;Permanently:</strong> ‘영구적으로 이동했다’는 뜻으로 Location 헤더 값에 명시된 URL로 리다  
이렉션된다. 보통 URL 입력 시 디렉터리 이후 / 문자가 붙지만 이를 붙이지 않고 요청할 경우 301 상태 코  
드가 전달된다.  
<strong>●&nbsp;302&nbsp;Found:</strong> 요청한 URL에 대해 Location 헤더 값에 명시된 URL로 리다이렉션되며, 임시로 가리키기   
위한 목적으로 사용한다. 301과 기능은 비슷하지만 301은 영구적, 302는 임시적이라는 차이가 있다. 보통   
권한이 필요한 페이지에 비인가자(로그인이 되지 않은) 상태로 접속할 경우 302 상태 코드를 반환하도록 구  
현하는 경우가 많다.  
<strong>●&nbsp;304&nbsp;Not&nbsp;Modified:</strong> 수정되지 않았음을 나타내는 상태 코드다. 클라이언트는 접속한 사이트의 이미지, 텍  
스트, HTML 등 정적인 자원을 이미 가지고 있다. 사용자가 메뉴를 이동하거나 해당 사이트에 재접속하면 정  
적 자원을 다시 요청하는데 이때 서버 측은 해당 자원이 변경되지 않았다고 알리고, 브라우저는 자신이 가진   
원본 자원을 이용해 페이지를 출력한다. 해당 상태 코드 값이 세팅된 응답 메시지에 엔티티 본문은 포함하지   
않는다. 앞서 300번대는 리다이렉션 상태 코드라고 했지만, 304는 리다이렉션과 관련이 없다.  
<strong>●&nbsp;400&nbsp;Bad&nbsp;Request:</strong> 요청 메시지의 구문이 잘못되었음을 알려 주는 상태 코드다.  
<strong>●&nbsp;403&nbsp;Forbidden:&nbsp;</strong> 요청이 서버에 의해 접근이 거부되었음을 알려 주는 상태 코드다. 원인은 파일에 대한 권  
한이 부여되지 않았거나 접근 권한을 설정했을 때, 디렉터리 접근 시 index 파일이 없다면 403 상태 코드를   
볼 수 있다.  
<strong>●&nbsp;404&nbsp;Not&nbsp;Found:&nbsp;</strong> 요청한 자원을 서버 측에서 찾을 수 없다는 것을 알려 주는 상태 코드다.  
<strong>●&nbsp;500&nbsp;Internal&nbsp;Server&nbsp;Error:&nbsp;</strong> 서버에서 요청을 처리하는 중 문제가 발생했다는 것을 알려 주는 상태 코드  
다. 서버 측 소스 코드의 에러 혹은 서버 측에서 자원 처리를 하지 못할 때 발생한다.

웹 서버 혹은 웹 애플리케이션은 서버별 400번대, 500번대 상태 코드에 대한 기본 에러 페이지가 다르다. 이를 통해 어떤 웹 서버 혹은 웹 애플리케이션 서버를 사용하는지 추론할 수 있고, 500 에러 발생 시 상세한 에러 노출로 일부 소스코드나 서버 측 절대 경로 노출 등으로 공격자에게 힌트를 제공하기도 한다. 이로 인해 대부분 사이트는 기본 에러 페이지가 아닌, 자체적으로 만든 페이지를 출력하여 정보 노출을 최소화한다.

#### <strong>6. 메시지 헤더</strong>

메시지 헤더는 메시지를 구성하는 요소로, 클라이언트와 서버가 무엇을 할지 결정하고 처리하기 위한 정보들이 있으며 반드시 요청 메시지와 응답 메시지에 포함되어 잇다. 메시지 헤더는 <strong>헤더명</strong>과 <strong>헤더 값으</strong>로 구성되어 있고, <strong>콜론(:)</strong>으로 구분한다.

메시지 헤더는 일반 헤더, 요청 헤더, 응답 헤더, 엔티티 헤더, 확장 헤더까지 크게 5가지로 나뉜다. 확장 헤더는 HTTP 명세에 추가되지 않은 비표준 헤더다.

#### <strong>일반 헤더</strong>

일반 헤더는 기본적인 정보를 제공하는 헤더로, 요청 메시지와 응답 메시지에 사용한다.

#### <strong>7. 쿠키와 세션</strong>

HTTP 프로토콜은 상태를 유지하고 관리할 수 없는 <strong>비연결성</strong>과 <strong>무상태</strong>라는 특성을 가지고 있어 프로토콜 레벨에서 다음 요청 때 동일한 사용자인지 알 수가 없다. 이때 사용하는 것이 쿠키다. 쿠키를 통해 사용자 식별, 클라이언트와 서버 간의 상태 유지 및 관리를 한다. 

클라이언트와 웹 서버는 요청 메시지와 응답 메시지를 주고받으면서 서로 통신하는데, 클라이언트 측에서는 <strong>Cookie 헤더</strong>를 통해 자기가 누구인지 증명하고, 웹 서버 측에서는 쿠키 발급 시 <strong>Set-Cookie 헤더</strong>를 사용한다.

Cookie 헤더는 서버로부터 발급받은 쿠키 정보로, 요청 메시지의 헤더에 세팅된다. Set-Cookie 헤더는 상태 관리를 개시하기 위한 헤더로, 클라이언트로부터 유요한 아이디, 패스워드로 인증을 요청할 경우 Set-Cookie 헤더를 통해 쿠키를 발급한다.

Set-Cookie 헤더의 속성은 cookie-name=cookie-value, expires, path, domin, secure가 있다.

● cookie-name=cookie-value: (필수 속성) 쿠키 이름과 값을 나타낸다.

● expires: (선택적 속성) 쿠키의 생명 주기를 날짜로 나타낸다. 해당 날짜가 되면 쿠키는 삭제되어 서버로 전달되지 않는다. 만약 해당 속성이 지정되지 않으면 세션 쿠키로 취급된다.

● path: (선택적 속성) 서버의 특정 경로에만 쿠키를 전달한다.

● domain: (선택적 속성) 기술된 도메인으로만 쿠키를 전송한다.

● secure: (선택적 속성) 보안 연결인 HTTPS 프로토콜을 사용할 때만 쿠키가 전송되는 속성이다. 사용할 경 우 쿠키가 전송된다.

Cookie 헤더는 웹 서버로부터 전달받은 cookie-name=cookie-value의 값을 세팅한다. 여러 개의 값을 세팅할 수 있으며 <strong>세미콜론(;)</strong>으로 구분한다.

쿠키 종류는 <strong>지속 쿠키</strong>와 <strong>세션 쿠키</strong> 크게 2가지로 나눌 수 있다. 흔히 쿠키라고 부르는 것이 지속 쿠키며, 세션이라고 부르는 것이 세션 쿠키다.

#### <strong>지속 쿠키</strong>

<strong>지속</strong> <strong>쿠키</strong>는 쿠키 정보가 클라이언트의 하드 디스크에 저장되어 웹 브라우저를 닫거나 컴퓨터를 재부팅해도 남아 있다.

> <strong><span style="color: #000000;">문제점</span></strong>
{: data-ke-style="style2"}

1\. 지속쿠키는 쿠키를 폐기하더라도 Set-Cookie 헤더를 통해 웹 브라우저의 쿠키 정보를 삭제하는 것뿐이고, 여전히 쿠키 정보는 웹 서버에 유효하다는 것이다.

2\. 쿠키 정보인 id=crehacktive 값만 들고 있다면 언제든 재사용이 가능하다.

3\. 별도의 타임아웃이 존재하지 않기 때문에 쿠키 정보가 공격자에게 노출될 확률이 커진다.

4\. 쿠키 정보를 탈취해서 사용자 계정을 무단 도용하는 쿠키 재사용 공격이 가능해진다.

5\. 쿠키 변조 공격에 취약하다.

> <strong><span style="color: #000000;">해결책</span></strong>
{: data-ke-style="style2"}

1\. 쿠키를 통해 사용자 식별 및 인증 관리를 할 경우, 평문으로 된 쿠키 정보를 반드시 암호화시켜야 한다.

2\. 장시간 노출에 따른 쿠키 재사용 위협을 방지하기 위해 타임아웃 검증 로직을 고려해야 한다.

#### <strong>세션 쿠키</strong>

<strong>세션 쿠키</strong>는 임시로 발급되는 쿠키로, 지속 쿠키와는 다르게 웹 브라우저를 닫으면 삭제될 뿐만 아니라 웹 서버 측에서 제어하기 때문에 지속 쿠키보다는 보안성이 뛰어나다.

#### <strong>지속 쿠키 vs </strong> <strong>세션 쿠키</strong>

세션 쿠키의 장점은 웹 서버에서 정보를 관리하기 때문에 지속 쿠키보다 안전하다는 것이다. 그러나 사용자가 많을수록 처리해야 할 정보량이 많아져 웹 서버의 부하는 증가할 수밖에 없다. 따라서 사용자가 많은 웹 서비스라면 세션 쿠키를 사용하는 것이 부담스러울 것이다.

반면 지속 쿠키는 정보 자체를 쿠키가 가지고 있고, 웹 서버는 쿠키의 암호화 여부에 따라 복호화를 해주고 별도의 로직에 따른 절차만 존재한다. 따라서 웹 서버에는 부하가 없다. 이러한 이유로 사용자가 많은 웹 서비스는 세션 쿠키가 아닌 지속 쿠키를 많이 사용한다.

#### <strong># 데이터 처리 방식</strong>

#### <strong>1. 인코딩과 디코딩</strong>

> <strong>인코딩</strong>
{: data-ke-style="style2"}

송수신 과정에서 데이터는 정확하게 전달되어야 하며 손실이 없어야 한다. 그리고 전달된 데이터가 구조화된 포맷일 경우 더 쉽게 원하는 데이터를 추출할 수 있게 된다. 이를 위해 원본 데이터를 특정 형태, 형식으로 변환이 필요한데, 이 변환 과정을 <strong>인코딩</strong>이라고 한다.

> <strong>인코딩과 암호화</strong>  
> 인코딩과 암호화는 다르다. 그 이유는 어떤 방식으로 인코딩 되었는지를 알면 디코딩을 해서 원본 데이터 확인이 가능하기 때문이다. 암호화는 데이터가 제3자에게 노출되지 않기 위해 데이터를 변환하는 기술로, 인코딩과는 기능적으로 역할이 다르다.
{: data-ke-style="style3"}

> <strong>디코딩</strong>
{: data-ke-style="style2"}

변환된 데이터를 다시 원본 형태로 변화하는 것을 <strong>디코딩</strong>이라고 한다. 이때 인코딩 전의 원본 데이터와 디코딩한 후 데이터는 변화가 없어야 한다.

#### <strong>2. URL 인코딩</strong>

<strong>URL 인코딩</strong>은 웹 브라우저에서 웹 서버로 데이터 전송 시 원본 데이터를 손실 없이 정확하게 전달하기 위해 사용한다. URL 인코딩을 <strong>퍼센트 인코딩</strong>이라고도 부른다.

#### <strong>URL 인코딩이 필요한 이유</strong>

URL은 ASCII 문자 집합을 사용한다. 영어 알파벳과 숫자, 몇 가지 특수 문자와 같이 일부 문자만 포함하고 있어 한글이나 일본어와 같은 여러 나라 언어에 대한 문자를 지원하지 않는다. 그리하여 ASCII 문자 집합 외 UTF-8, EUC-KR 등의 다른 문자 집합과 URL 예약 문자들을 데이터로 이용할 때 올바르게 전송하기 위해 사용한다.

#### <strong>URL 인코딩 문자 구조</strong>

URL 인코딩 된 문자는 URL에서 지원하는 ASCII 문자 집합 범위 내에서 변환되어야 한다. URL 인코딩은 % 문자와 그 뒤에 오는 두 자리 16진수로 구성된다. 이 16진수는 변환하려는 문자의 ASCII 값을 나타내며, 인코딩 된 문자는 URL에서 허용되지 않는 문자를 안전하게 전달하기 위해 사용한다.

#### <strong>3. Base64</strong>

<strong>Base64</strong>는 바이너리 데이터를 ASCII  문자 집합으로 변환하기 위해 사용하는 인코딩 방식이다. 바이너리 데이터란 이진수로 구성된 데이터로, 이미지, 실행 파일 등이 있다. 바이너리 데이터를 다뤄야 할 경우 대부분 Base64를 사용한다.

#### <strong>Base64를 사용하는 이유</strong>

Base64 인코딩을 하면 데이터의 길이가 원본보다 약 30% 늘어난다. 다만 Base64는 서로 다른 시스템 간 데이터를 전송할 때 유용하다. 시스템 간 바이너리 데이터를 처리하는 방식이 다르면 원본 데이터가 올바르게 전송되지 않기 때문에 어떠한 시스템이든 적합한 ASCII  문자 집합으로 이루어진 Base64를 사용하는 것이다. 따라서 Base64는 서로 다른 시스템 간 데이터 전송 시 데이터를 안전하게 전달하는 인코딩 방식이라고 할 수 있다.

#### <strong>Base64 문자 구성</strong>

Base64는 총 64개의 문자로, 알파벳 대소문자, 숫자, +, /로 구성되어 있다. = 문자는 패딩문자로, 뒤에 자릿수를 채우기 위해 0을 붙이는데 이를 = 문자로 표기하며, 문자의 맨 뒤에 위치한다.

#### <strong>Base64 변환 과정</strong>

우선 우너본 데이터를 이진수로 변환한 후 24비트 단위로 묶는다. 만약 빈자리가 있다면 0으로 채운다. 그리고 6비트 단위로 나누고 Base64 색인표의 인덱스 값과 매핑되는 값의 문자로 치환한다. 만약 6비트 모두 0일 경우 패딩 문자인 =로 치환된다.

#### <strong>Base64 URL-Safe</strong>

Base64 인코딩에 사용하는 문자 중 +는 예약 문자인 공백이고 /는 경로를 구분한다. 때문에 URL에 사용할 경우 안전하게 사용하기 위해 + 문자는 -로, / 문자는 \_로 치환된다. 이러한 인코딩을 Base64 URL이라 부른다.

#### <strong>4. JSON</strong>

<strong>JSON</strong>은 키와 값으로 이루어진 텍스트 기반의 데이터로, 데이터를 쉽게 전달하고 읽고 수정할 수 있다. JSON은 단순해서 가독성이 뛰어나고, 경량 데이터 형식등의 이유로 서버와 클라이언트 통신 시 메시지 규격으로 많이 사용한다.

#### <strong>5. XML</strong>

<strong>XML</strong>은 데이터를 효율적으로 전달, 저장하기 위한 마크업 언어로, JSON과 동일하게 클라이언트와 서버 간의 데이터를 전달하는 용도로 많이 사용햇으나 오늘날에는 JSON의 사용률이 높아지고 있어 점점 줄고 잇는 추세다. 그러나 여전히 XML을 기반으로 사용하는 곳이 많다.

#### <strong>XML의 특징과 구조</strong>

XML은 마크업 언어이므로 HTML과 동일하게 태그를 사용하지만, 가장 큰 차이점은 XML의 태그는 사용자가 직접 정의한다는 것이다. 또한, XML은 HTML과 달리 대소문자를 구분하며, 태그를 닫아야 한다. 언어의 용도도 다른데, XML은 데이터 교환과 처리 목적으로 많이 사용하지만, HTML은 웹 페이지 구조를 만드는 역할을 한다.

XML은 루트 요소부터 자식 요소로 연결된 트리 형태의 계층 구조를 가진다. 첫 줄에는 XML 태그 &lt;?xml version="1.0 encoding="UTF-8"?&gt;을 통해 XML 문서임을 명시해야 한다.
